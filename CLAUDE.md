# CQA Hackathon (Freedom Broker): бриф для агентов команды

> Ты агент одного из участников команды. Прочитай этот файл целиком до того, как писать код.
> Если что-то здесь противоречит заданию в docs/, верно задание. Заметил противоречие — исправь этот файл.

## 1. Что строим
Прототип Conversation Quality Analytics (CQA): ИИ оценивает работу оператора поддержки по настраиваемому чек-листу,
результат можно оспорить через апелляцию. Срок 24 часа, защита 5 минут.

Источники истины:
- docs/CQA_Hackathon_Student_Guide.pdf: задание, требования, тайминг
- docs/CQA_Chat_Quality_Checklist.pdf: стартовый чек-лист (8 критериев, веса, шкалы, правила N/A)
- data/DEV.json: снапшот DEV-набора (65 диалогов), ответ API как есть (имя = group_id, его читает `npm run eval`)

### Обязательные функции
Контур 1 · Оценка
1. Редактор чек-листа: добавить, изменить или удалить критерий, его формулировку, вес, тип ответа (Да/Нет или шкала),
   флаг «N/A разрешён» с условием, ступени шкалы, секцию. Сохраняется как новая версия.
2. Оценка диалога: выбрать диалог (или пакет) и чек-лист, запустить LLM. Языки RU, KZ, EN.
   Реплики bot и system служат контекстом, оценивается только operator.
3. Результат: по каждому критерию ответ, баллы, вес, объяснение и ссылка на реплику-доказательство.
   Для «Нет» — какой участок проверен, для N/A — причина. Итог, итоги по секциям, отдельный флаг грубой ошибки.

Контур 2 · Работа с результатом
4. Карточка: список → транскрипт и оценка. Клик по доказательству прокручивает к сообщению и подсвечивает его.
   У звонков плеер перематывается на момент реплики.
5. Апелляция: выбрать критерий, написать комментарий, сохранить.
6. Решение проверяющего: подтвердить или изменить оценку с причиной, итог пересчитывается.
   В карточке видны исходная оценка, решение и финальный результат. Авторизации нет: роль — переключатель в UI.

## 2. Данные (уже проверено)
API: GET <URL организаторов>&group_id=DEV. Полный URL с подписью не коммитим: `.env` → `CQA_API_URL`,
group_id передаём параметром. Из браузера CORS, поэтому только через бэкенд.

{ "error": "", "isSuccess": true, "data": { "dataset_group_id": "DEV", "total_records": 65,
  "records": [{ "conversation_id": "p1-ru-001", "channel": "agent chat" | "voice call",
     "language": "RU" | "KZ" | "EN",
     "transcript": [{ "timestamp": "00:02", "speaker": "client|operator|bot|system", "text": "..." }],
     "audio_url": null | "https://..." }] } }

- 60 чатов (p1-ru-001..030, p1-kz-001..015, p1-en-001..015) и 5 звонков RU (p4-ru-001..005). 11–115 реплик, в среднем ~20.
- Типичный чат: клиент → бот AIM (приветствие, согласие на ПД) → клиент просит оператора → system «Эскалация на оператора» /
  «Чат операторға жіберілді» / «Chat transferred to an agent» → operator. Приветствие бота не засчитывается оператору.
- Важные системные события (на них ссылаемся как на доказательство):
  - идентификация: «Личность клиента подтверждена.» / «Клиенттің жеке басы расталды.» / «Customer identity verified.»;
  - обрыв: «Соединение с клиентом прервано.» / «Клиент покинул чат.» / «Connection to customer lost.»;
  - закрытие: «Оператор закрыл чат.» / «Agent closed the chat.» / «Клиент завершил разговор.»;
  - удержание: «Клиент находится на удержании».
- Время: в чатах MM:SS, в звонках ISO 8601 с TZ. Исходные метки не меняем. Смещение для плеера = t − t(первой реплики), сек.
- Звонки: транскрипт ASR с ошибками, ПД замаскированы ([Имя скрыто], [Персональные данные скрыты]). Есть паузы записи.
  Маскирование ПД не считается раскрытием.
- `audio_url` отдаёт HTML-страницу с <audio><source src="...">; SAS-ссылка живёт ~1 час. Бэкенд по запросу
  вытаскивает свежий src регэкспом. Запасной вариант: кнопка «открыть плеер».

## 3. Чек-лист и формула
Стартовая конфигурация: `server/seed/checklist.default.json` (8 критериев, секции s1–s4).
Описания ступеней шкал c04 и c06 перенесены из PDF стр. 2. В c02 уточнено, когда «Нет», а когда N/A.

Формула реализована в `server/scoring.js` (детерминированно, не в LLM), тесты в `server/test/scoring.test.js`:
- применимы критерии с kind ≠ gross, weight > 0 и ответом ≠ na/manual;
- fraction: yes/no → 1/0 (для `polarity:"negative"` наоборот: «Да» = нарушение → 0); scale → value / max(levels);
- итог = round(Σ weight·fraction / Σ weight · 100, 2), если Σ weight = 0 → null;
- секции: своя нормировка (`total`) и вклад в общий итог (`contribution`);
- gross_error = любой kind="gross" ответил «Да»; на балл не влияет;
- `answer: "manual"` = модель не дала валидный ответ, критерий исключается и попадает в `pending_manual`.

## 5. LLM (server/llm/)
- Провайдер: OpenAI Chat Completions, `response_format: json_schema` со `strict: true` (`provider.js`). Модель, ключ,
  reasoning_effort/temperature и цены — только из `.env`. Интерфейс провайдера: `complete({messages, schema}) → {json, usage, model}`.
- `events.js` — разметка событий до вызова (первая/последняя реплика оператора, эскалация, идентификация, обрыв, удержание,
  закрытие, паузы записи, долгий ответ ≥ 120 с) + смещения для плеера. Не привязано к критериям.
- `prompt.js` — системный промпт с общими правилами + чек-лист из конфига (стабильный префикс для кеша провайдера),
  затем события и нумерованный транскрипт `[12] 03:02 operator: текст`. Схема ответа строится из конфига:
  enum ступеней шкалы, `na` только при na_allowed, поле reasoning идёт перед answer, плюс `operator_name`.
- `validate.js` — допустимость ответа, N/A, индексы в пределах транскрипта (лишние отбрасываются).
- `evaluate.js` — `evaluateConversation({record, checklist, provider, runs, group_id})` → Evaluation без id.
  N прогонов (LLM_RUNS, по умолчанию 3) параллельно, в каждом один повтор при ошибке; голосование по каждому критерию
  (большинство; ничья на шкале → медиана); `confidence` = доля голосов; нет валидных ответов → `"manual"`.
  Сохраняются usage, cost_usd, events, score.
- CLI: `npm run eval -- --group DEV [--ids a,b] [--limit 5] [--runs 3]` (читает `data/<group>.json`, пишет в хранилище).
- Точность: разметка в `data/gt/<conversation_id>.json` = `{ "conversation_id", "answers": { "<criterion_id>": "yes"|"no"|"na"|<число> } }`,
  плюс `ambiguous` (спорные критерии) и `note`. `npm run accuracy [-- --verbose 1]` — совпадение по критериям, без спорных,
  по языкам, N/A precision/recall, ошибка шкалы и итога, совпадение флага, расхождения (с объяснением модели в --verbose).
- Эталон: 41 диалог DEV в трёх наборах (см. ниже). **Черновик разметки ИИ-ассистента — проверить человеку**
  (особенно KZ), иначе цифры точности завышены. Соглашения разметки — `data/gt/README.md`.

### Замеры точности (07.11, эталон — черновик разметки ИИ, проверить человеку)
Три набора, чтобы не подгонять промпт под одни и те же диалоги:
- `data/gt` — настроечный (20: 12 RU / 4 KZ / 4 EN): по нему разбираем ошибки и правим формулировки;
- `data/gt-holdout` — контрольный (13: 6 RU / 3 KZ / 3 EN / 1 звонок): только для проверки;
- `data/gt-fresh` — свежий (8, размечен после всех правок, в основном «чистые» диалоги).
Запуск на любом наборе: `npm run eval -- --ids <id,...> --runs 3` → `npm run accuracy -- --gt data/gt-holdout --verbose 1`.

Совпадение по всем 41 диалогу (328 ответов), до и после уточнения формулировок c02/c06/c07 в чек-листе:
| Модель | Прогонов | До | После | $ за диалог |
|---|---|---|---|---|
| gpt-6-luna (low) | 3 | 89.9% | **92.1%** | 0.0018 |
| gpt-6-luna (medium) | 3 | — | ≈ как low | 0.0028 (не стоит того) |
| gpt-6.1-sol (low) | 1 | 93.6% | 93.3% | 0.011 |

- Грубые ошибки — 100% на всех наборах; N/A без ложных срабатываний.
- Оставшиеся расхождения почти все в критериях, помеченных в эталоне как спорные (c04/c05/c06): дальше точность
  упирается в качество разметки, а не в модель. Следующий шаг — человек проверяет эталон, особенно KZ и звонок.
- Полный DEV (65) на gpt-6-luna × 3: 75 с, $0.11, 0 сбоев, 0 manual, кеш промпта 97% входных токенов,
  те же 8 грубых ошибок; 10% ответов с confidence < 1 — их подсвечивать в UI как «проверить».
- Что помогло (в конфиге чек-листа, промпт остаётся общим): c06 — формулировка из PDF вместо «без лишних задержек»,
  что такое «явное ожидание», когда ставить 4; c07 — вежливая формула не итог; c02 — полнота ответа не здесь.
  Плюс правила 10–12 в SYSTEM_PROMPT. Что не помогло: reasoning medium, голосование для Sol.

По умолчанию `gpt-6-luna`. Для демо и контрольного набора можно `gpt-6.1-sol`, LLM_RUNS=1 (≈ $0.75 за 65 диалогов,
+1 п.п.), не забыв цены LLM_PRICE_* в `.env`.

## 7. Демо (5 минут)
1 мин: интерфейс, сводка руководителя, выбранный диалог. 2 мин: оценка, обоснование, переход к реплике, N/A, итог.
1 мин: апелляция, решение проверяющего, новый итог, тревога о грубой ошибке. 1 мин: замена критерия в UI и повторное применение.

## 8. Вопросы организаторам и принятые решения
Решено:
- Звонки оцениваются тем же чек-листом из 8 критериев, что и чаты.
- Транскрипты в контрольном наборе будут всегда; свой ASR не нужен.

Открыто (до ответа действуем по допущению):
1. Как сравнивают с GT (итог / каждый критерий / N/A / флаг)? → оптимизируем совпадение по каждому критерию.
2. Можно ли эталон 3–5 DEV-диалогов? → размечаем сами 10–15.
3. Есть ли база знаний для c04? → нет: оцениваем по внутренней согласованности, непроверяемые факты не штрафуем.
4. Завершение: хватает ли одного прощания? → нет, нужно прощание + (итог или предложение помощи).
5. Ошибки ASR и скрытые ПД в звонках → ASR не штрафуем; «[скрыто]» после запроса оператора = данные названы.
6. Точка отсчёта аудио → t − t(первой реплики); проверить на одном звонке, сдвигают ли паузы записи.

## 9. Бизнес-функции
- **Профиль оператора** `#/operators/:name`: средний балл против команды, динамика, слабые критерии, диалоги,
  ручное исправление имени. Оператор = `operator_name` из оценки → ручное имя → «Не определён».
- **Тревоги** `#/alerts`: лента грубых ошибок с объяснением и ссылкой на реплику, «отметить как просмотренное» с заметкой, бейдж в меню.
- **Сводка руководителя** `#/dashboard`: средний балл, грубые ошибки, апелляции (% удовлетворённых), ручная проверка,
  стоимость; проблемные критерии; распределение; разрезы по языкам, каналам, операторам; таблица по всем критериям.
- Аналитика учитывает последнюю оценку каждого диалога и решения по апелляциям; критерии берутся из версии чек-листа
  оценки, поэтому новые/заменённые критерии появляются автоматически.

## Текущее дополнение: фронт и демо

- Реализованы `checklists.js`, `appeals.js`, `list.js`, `conversation.js`, переключатель роли в шапке.
- `GET /api/datasets/:groupId` сейчас читает **локальный** снапшот `data/<groupId>.json`; загрузка API организаторов не реализована. Для тестов каталог можно задать через `DATA_DIR`.
- `POST /api/evaluate` принимает также `checklist_version`, обрабатывает до 5 диалогов одновременно и возвращает `{evaluations, errors}` после завершения (потокового прогресса пока нет).
- `GET /api/evaluations/:id` дополнен `final_score`: учитывает все решения, исходные `results` и `score` сохраняются.
- Решение по закрытой апелляции повторно не принимается; ответ проверяется по сохранённой версии шкалы/N/A.
- Сценарий и план репетиции: `docs/DEMO.md`. Ступени c04/c06 сверены с отдельным PDF чек-листа в docs/.
